# TUI feature requests, 2026-09-23: detail

Full detail for the "New requests (2026-09-23)" entries of
`docs/tui_feature_requests_from_human.md`. The index keeps one line
per request. This doc keeps the request text, the decision, the
shipped notes, and the test names.

## tree-fold-jump

- [x] The tree palette needs fold/unfold and a jump to the
      next/last branch starting point. The user's words: "add
      shortcut to fold/unfold the tree, jump to the next/last
      branch starting point. The keybinding can reuse the fold mode
      keybinding in browse mode."
      Decision 2026-09-23: reuse the browse-mode fold key set.
      `z` arms, the next character acts. The tree has no turn
      folds, so the second-key mapping is:

      | key | browse meaning | tree meaning |
      |---|---|---|
      | `za` | toggle the fold under the cursor | fold/unfold the innermost branch under the cursor |
      | `zo` | open the fold under the cursor | unfold that branch |
      | `zc` | close the fold under the cursor | fold that branch |
      | `zR` | open all folds | unfold every branch |
      | `zM` | close all folds | fold every branch, trunk rows stay |
      | `zj` | next fold | next branch boundary |
      | `zk` | last fold | last branch boundary before the cursor |
      | `zA` | toggle tool results in the turn | unbound in the tree, flashes |

      A branch boundary is a rewind marker row, or the head of the
      abandoned tail of the branch it starts (the first visible row
      after the marker's target, see `tree-input-focus` below). The
      request's "next/last" is wired as next/previous, so `zk`
      lands on the boundary just before the cursor. An unbound
      second character flashes and drops the arm. The arm acts only
      while a view focus is held; with the filter input focused,
      every character types into the query (see `tree-input-focus`
      below). The tree starts fully expanded, as before. The `z`
      arm is opt-in folding on top of that.
      Shipped 2026-09-23: `SessionTree` gained `parent_of`,
      `has_children`, `is_marker`, `foldable_seqs`,
      `marker_target`, and `tail_head` in
      `bin/tui/src/palette/tree_model.rs`. `App` gained
      `tree_folded` (the folded branch-point seqs, reapplied over
      the frame expand-all) and `tree_z_armed`, a state-based arm
      flag with no TTL, plus `tree_fold_key`, `tree_fold_target`,
      and `apply_tree_folds` in `bin/tui/src/app.rs`. `z` and an
      armed second character route through the tree-stage key
      table in `App::press`, gated on view focus. Fold state
      resets with the tree view on a session switch or a new tree
      visit, like the view state.
      Tests: `tree_fold_tests` in `bin/tui/src/app.rs`
      (`tree_stage_starts_fully_expanded`,
      `zc_folds_the_branch_under_the_cursor`,
      `zm_zr_fold_all_branches`,
      `zj_zk_jump_between_branch_boundaries`,
      `zj_reaches_the_abandoned_tail_head`,
      `fold_state_resets_on_session_switch`,
      `view_focus_keeps_chars_out_of_the_filter`,
      `input_focus_types_z_into_the_query`) and
      `marker_targets_and_tail_heads` in
      `bin/tui/src/palette/tree_model.rs`.

## tree-input-focus

- [x] The user rejected the time-based fold arm. Their words: "I do
      not like the buffered version. 3s is too long. I need a
      completely disambiguated approach. Perhaps we need to
      implement the modal model in the floating window. Or, just
      like `Shift+Tab` to switch focus between the tree view and
      preview pane, we can introduce a keybind to switch focus
      between the command input queue and the tree view."
      Decision 2026-09-23: the focus model, the user's second
      option. `Focus` gains an `Input` target (the command input
      queue). The existing cycler (`Shift+Tab` / `Ctrl+Shift+P`,
      item 4 of docs/tree-ui-design-from-human-phase-2.md) walks
      `Input -> List -> Preview -> Input` in the tree stage; other
      stages keep the plain `List <-> Preview` toggle. The tree
      stage opens on `Input` focus, so the first key types. With
      `Input` focus every character reaches the query, including
      `z`. With `List` or `Preview` focus the `z` arm is live and
      plain characters do not reach the query; they flash a hint
      instead. The arm is state-based, no TTL: it clears on the
      resolving character, any movement or commit key, a focus
      switch, or `Esc`.
      Shipped 2026-09-23: `Focus::Input` in
      `bin/tui/src/float.rs`. `PaletteState::toggle_focus`
      (`bin/tui/src/palette/state.rs`) cycles all three targets in
      the tree stage; `goto_tree_list` starts on `Input`. The
      tree-stage routing in `App::press`
      (`bin/tui/src/app.rs`) gates the fold arm on view focus and
      routes plain characters to the query only in `Input` focus.
      The input bar shows an `input focus` hint. `zj`/`zk` now
      jump to branch boundaries: marker rows and abandoned-tail
      heads (the user's follow-up question, "why can't I jump to
      the head of the abandoned tail").
      Tests: `tree_stage_focus_cycles_three_targets` and
      `input_focus_toggles_with_the_pane_hidden` in
      `bin/tui/src/palette/state.rs`, plus the `tree_fold_tests`
      and `marker_targets_and_tail_heads` cases named under
      `tree-fold-jump`.
